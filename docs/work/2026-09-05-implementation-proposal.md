# Kindle Agent 看板：V13 功能实现方案

日期：2026-09-05。状态：项目复核与方案整理完成；以下架构是建议，功能实施尚未开始，Kindle 设备排查仍暂停。

## 目标与范围

将已经定稿的 V13 做成日常使用的横屏信息看板：本地时钟、天气、日期/农历、当天日程与待办、月历与事件点、节气/黄历、未来七天安排；支持便签、Agent 简报和照片轮播。

保持 V13 的 1448×1072 横屏布局、左右分区、字号层级、图标位置和黑白风格。亮度在左下、设置在右上可点；右下 Wi-Fi 与电池只显示。功能化需要将静态文字和图标绑定真实数据，但不重新设计页面。新简报/照片页独立增加，不把主页面塞满。

本轮交付仅为代码复核和方案。不安装设备程序、不接入账号、不部署 NAS；也不以本轮规划作为自动恢复此前设备排查的授权。

## 推荐架构

**Kindle 本地负责显示与交互；可选的轻量服务负责账号同步、内容整理和 Agent 接入。**

```text
本机时间 / 电池 / Wi-Fi / 本地便签 ────────────────┐
天气 HTTPS / 可选订阅适配器 ─────────────────────┤
                                              ↓
Apple / Google → 连接器 → 小服务 → 数据快照 → Kindle 缓存 → V13 本地界面
Agent ─────────────────→ 内容卡片 ───────────────┘
本地照片 / 图片来源 ─────→ 处理后的图片资源 ────────┘
```

决定性原因是时钟、亮度、断网使用和触摸都属于设备能力。每分钟下载一张完整截图虽然易做，但无法自然解决这些要求。让完整桌面浏览器或 Python 服务驻留在 PW3，则增加启动、内存和系统适配负担。

### Kindle 端

- 优先基于已安装的 KOReader v2026.03，做 Lua 自定义全屏组件；当前的“打开 PNG”插件仅是历史预览入口，不是最终应用。
- 复用 KOReader 的字体/图像绘制、手势、计时、局部刷新、亮度、电池与网络接口。已在本地对应版本源码找到这些接口，但本机适配仍需实测。
- V13 的文字、日期网格、天气和状态在本地按固定坐标绘制；照片使用预处理图片。保留现有 Python V13 作为电脑预览与版式参照，不能把服务端 PNG 是否生成当作设备刷新成功。
- 提取一份 V13 布局参数和图标资源，供设备与电脑预览使用。先核对现有字体可用性与字宽；若分发需替换为可再分发字体，必须另验换行和字号效果，不把系统字体直接打包给他人。
- 亮度通过 KOReader 设备接口调节；PW3 的“最低亮度”与“彻底关灯”存在硬件适配差异，本地源码已有处理，避免直接套用统一的 0–24 数值。
- 显示由 KOReader 单独管理，不同时启动另一个 FBInk 守护进程抢屏。FBInk 直绘保留为有证据后再评估的备选方案。
- 设置弹层管理城市、数据源、轮播、前光、同步状态、日志导出和退出；日志不写令牌或完整个人日程。
- 设备取得资料后先校验、再原子替换缓存；联网任务有超时并在后台执行，不阻塞触摸与时钟。

### 三种运行方式

| 模式 | 能得到什么 | 现实边界 |
| --- | --- | --- |
| 仅 Kindle | 时钟/月历、农历节气、本地待办便签、联网天气、本地图片；后续增加受支持的 ICS 订阅 | 私有 Apple/Google 账号、复杂认证和完整周期事件同步不列入基础版承诺 |
| Kindle + Mac | 完整显示 + Apple 日历/提醒事项连接器 + Agent 内容；小服务可作为普通进程运行 | Mac 休眠时，新的 Apple 数据与 Agent 内容暂停；Kindle 使用本地缓存 |
| Kindle + NAS Docker | 常驻同步、Google/iCloud 日历、Agent 内容库、图片处理；便于备份与迁移 | Apple 提醒事项若使用 EventKit，仍需 Mac 连接器；Docker 不会赋予 Linux 访问 macOS 日历库的能力 |

推荐先完成 Kindle 本地基础版，再用现有 Mac 跑通真实数据，最后将同一小服务迁移至 NAS。这样保留“只有一台越狱 Kindle 也能用”的产品形态，同时使完整账号同步成为可选增强。

## 各功能如何实现

| 功能 | 推荐来源和行为 |
| --- | --- |
| 时间、日期、星期 | Kindle 系统时间，默认 Asia/Shanghai；分钟边界更新时钟，跨日重算日历/日程；不显示秒级跳动 |
| 月历、未来七天 | 由同一份事件缓存计算；月历查询范围覆盖可见的 42 个日期格，七天列表按当前日期滚动，今日反色与事件点独立计算 |
| 今日待办与日程 | 带时间项目合并排序；全天项目和无时间待办明确标识；保留所有条目，在原有列表区域内翻页，数据层不按屏幕行数截断 |
| 便签 | 第一阶段为本地/Agent 文本卡片；在简报页或已有区域的详情层显示。Apple 备忘录同步是另外的连接器，不等同于 Apple 提醒事项 |
| 天气 | Open-Meteo 等可达服务，按天气代码映射公开图标库；温度、高低温、降雨概率、UV、风速都取真实字段，缺失显示“--” |
| 农历、节气 | 采用维护中的算法库或可验证的历表，在支持日期范围内本地计算；闰月和节气时区须验证 |
| 黄历 | 使用明确注明来源的历表/数据源；无数据就显示暂无。不能把示例生活建议或 Agent 生成文字当作真实黄历 |
| 前光与状态 | 设置/亮度图标触摸可用，Wi-Fi/电池只读；Wi-Fi 已连接与日历已同步是两种状态 |
| 新闻/Agent 简报 | Agent 提交结构化卡片，附来源链接、发布时间、有效期；日程事实直接来自同步，不依赖模型重新编造 |
| 每日图片 | 支持本地上传或可用且允许使用的图片源，裁剪到屏幕比例并做灰度/抖动处理；保留来源信息，不把 Bing 图片接口可用性视为长期保证 |

“待办提醒”首版指展示待办及临近事项的视觉提示，不承诺 PW3 声音提醒或操作系统级通知。勾选完成并回写 Apple/Google 属于后续功能，首版默认只读同步。

### Apple 与 Google 的边界

**Apple 日历和提醒事项：**推荐先做小型 Swift/EventKit Mac 连接器，读取用户选定的系统日历和提醒事项列表，输出统一快照。需要首次系统访问授权。EventKit 支持读取两类信息；实际能看到哪些列表、共享项目和字段，需要在当前 Mac 上验证。未来连接器可把数据提交到 NAS，而无需让模型定时读一遍日历。

**iCloud 日历直接接 NAS：**使用 CalDAV 与独立应用密码等账户支持的认证方式。上线前验证发现日历、时区、重复事件、例外、删除与增量更新。不要将现代 iCloud 提醒事项支持视为 CalDAV 日历接入的附带能力。

**Google：**使用 Calendar API 和 Tasks API，授权与刷新令牌存于连接器宿主。首版请求只读范围；循环事件展开、分页、取消与更新时间纳入适配器。Google Tasks 的 `due` API 字段只保留日期，官方说明不能读写安排的具体时刻；这类待办应显示为无具体时间，不能自行填成 09:00 或 00:00。

**避免重复：**同一个 Google 日历若已经通过 Mac 系统日历同步，不同时从 Google API 再导入；每个日历指定一个主接入通道。不能仅按标题和时间去重，以免误删真实的相同会议。

## 数据与 Agent 接口

将现有演示 schema 演进为生产快照，而不是直接用展示字符串做数据库：

- 事件保留 `source / account / calendar / source_id / instance_id / start / end / timezone / all_day / updated_at / status`；全天结束日期按来源的排他语义处理。
- 待办保留 `source_id / title / scheduled_date / due_at / completed / priority`；没有时间就是空值。展示时间与来源原始字段分开。
- 来源状态保留最后成功同步时间、错误、覆盖日期范围；区分空列表、失败和取消，失败不能清空上一份数据。
- 显示快照携带版本、时区、数据范围、有效期与资源引用。月历事件点基于完整事件集，不能只取“未来五条”。
- Agent 卡片限定为简报、便签、图片和提示，包含 `id / type / title / body / source_url / published_at / expires_at / priority / display_seconds`。
- 首版只开放写入/撤回卡片、设置轮播与临时显示页面等有限动作。内容不能变成设备上的 Shell、Lua 或任意程序执行。

建议 API 边界为：设备只读 `GET /api/v1/snapshot` 和资源；Agent 使用独立凭据 `PUT /api/v1/cards/{id}` / `DELETE /api/v1/cards/{id}`，并通过 `POST /api/v1/display-intents` 提交带有效期的页面选择/轮播请求；Mac 连接器写入自己的来源快照。重复发送相同卡片或请求 ID 更新原条目，过期卡片自动移出轮播。设备凭据不能修改内容，Agent 凭据不能读取账号令牌。

用户体验是“Agent 推送到看板”；传输上先由 Kindle 每 30–60 秒查询版本，变化后才拉内容。刷新本身不调用模型。设备休眠时不会实时接收，恢复后检查有效期并更新；本轮不创建任何定时 Agent 任务。

## 刷新、轮播和离线

- 时钟：每分钟局部刷新；天气：约 30 分钟获取；日程/待办：连接器约 1–5 分钟同步；这些只是初始配置，真机验证后调整。
- 默认停在 V13；可启用“V13 → Agent 简报 → 每日图片 → V13”，建议先用 3 分钟 / 1 分钟 / 2 分钟，用户可调。进入设置、阅读详情或临近日程时暂缓轮播。
- 重要提示有时长与频率上限，过期后返回主页面；不能无限占屏或频繁闪烁。
- 局部更新与定期整屏去残影分开。全刷周期由 PW3 实测决定，不照搬其他机型波形配置。
- 断网后时钟、亮度、月历和已缓存事项继续工作；跨日按缓存日期范围重新筛选，不能把昨天的“今日安排”当今天显示。超出覆盖范围则显示未知/待同步。
- 过期内容在原有内容/详情区域标明截至时间，不增加永久调试页脚；Wi-Fi 图标不充当数据新鲜度保证。
- 接电常显模式保持界面运行，允许 Wi-Fi 常开；关盖/电源休眠模式保存状态并在唤醒后恢复。插 USB 存储期间停止访问用户分区，恢复后再加载。
- 墨水屏维持静态画面省电，但 CPU 常醒、Wi-Fi、前光及刷新都会耗电。不能同时保证每分钟时钟实时更新和长时间深度休眠；本项目优先用户提出的随用随充体验。

## 服务与部署

建议复用当前 Python 技术栈，增加一个轻量 HTTP 服务、周期同步任务和 SQLite。沿用 Pillow 做电脑预览及图片处理。无需 Redis、独立队列、多服务数据库或常驻模型；只有需要生成内容时才由已有 Agent 发起。

Mac 可直接运行普通进程并按需加登录启动项。NAS 用一个 Docker 容器与持久数据卷，包含配置、缓存、SQLite 和图片；服务代码与数据分开。连接器密钥不进入图片、日志、公共仓库或 Kindle 文件包。NAS 的 CPU 架构、端口、磁盘目录和 TLS 可达性在部署阶段核实，不预估为已验证。

Kindle 端需要实测当前网络库的 HTTPS 和证书能力；不能以关闭证书验证作为默认解决办法。手机/电脑配置界面承担账号登录与长便签输入，设备设置承担本地显示选项。

Apple EventKit 连接器是 Mac 本机进程，不能并入 Linux Docker 镜像。迁到 NAS 后，Google/iCloud 日历及已入库的 Agent 内容可独立工作；Apple 提醒事项的新变化依然受 Mac 连接器在线状态影响。


## 分阶段实施与验收

| 顺序 | 可交付结果 | 通过条件 |
| --- | --- | --- |
| 0. 设备运行验证 | 能打开/退出的最小 KOReader 看板组件，导出加载/初始化/点击/绘制日志 | 真机明确看到界面；亮度接口可用；退出恢复阅读；关盖、唤醒与 USB 切换恢复正常。失败先定位日志，不增加业务功能 |
| 1. V13 本地功能版 | 按原版式显示模拟的完整结构化数据；时钟、当天高亮、电量/Wi-Fi、前光、设置、离线缓存 | 连续运行及跨日有效；六周月历、跨月、全天/无时间/超过一屏项目显示正确；天气和 Agent 断开也能使用本地功能 |
| 2. 真实数据版 | Mac 连接器读取 Apple 日历/提醒事项；接天气；Google/CalDAV 作为替换或补充源 | 在手机修改后于配置同步窗口内更新；新增/取消/重复事件例外/空列表处理正确；源失败保留旧数据并标明时间 |
| 3. Agent 与轮播版 | 发布/撤回简报便签和图片，设置页面顺序与停留时间 | 不运行 Agent 时日历正常；重复提交不重复占位，过期撤回，设置操作不被切屏打断，断网不白屏 |
| 4. NAS 与分发版 | 同一服务打包 Docker；提供 Kindle 安装包、Mac 连接器与诊断说明；独立版增加验证过的订阅能力 | 容器重启数据保留；旧设备包可回退；明确各模式对 Mac 的依赖；移除插件后原阅读流程可用 |

实施先后由这些可见成果决定。不要把“菜单显示”或“成功复制文件”当作阶段 0 验收，也不要用静态 V13 截图代替阶段 1 的动态验收。首个完整使用里程碑是阶段 2；Agent/图片轮播随后增加。设备入口问题尚未知，不能据此承诺具体工期。
